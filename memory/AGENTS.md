# 記憶の設計ハーネス

**原則: 記憶は分けて隠すのではなく、層で置き場を決め、必要な時だけ取り出す。**
混乱の原因は共有ではなく「全記憶を毎回読むこと」。毎回読むのは索引1枚だけにする。
道具: `bin/memory.py`（コマンドはすべてハーネスのフォルダ基準）。

## 1. どこに書くか（3層）

記憶の実体: 既定 `data/memory/`（git管理外）。PC間で共有するなら `harness.config.local.json` の `memory_dir` を同期フォルダ（Drive等）へ向ける。

| 層 | 中身 | 置き場 | 読み方 |
|---|---|---|---|
| global | 全事業に効く事実（ユーザー像・安全/コスト規則） | 上記直下＋`MEMORY.md` に1行索引 | 毎セッション索引だけ |
| domain | 事業固有の事実（FX・受験・各社） | 上記直下（**索引に載せない**） | 検索で必要時のみ |
| agent | 特定の役割（社員）固有の知見 | `agents/<役割名>/` | 本人が検索で必要時のみ |

判断に迷ったら domain に置く（global は毎ターン費用がかかる）。

## 2. 書く前に決める4択

- `skip` … 既存と同じ／次回の判断を変えない → **書かない**（既定）
- `update` … 同じ事実のより良い版 → 既存ファイルを直す
- `merge` … 同じ事実が複数ファイルにある → 1本へ統合（日付は両方残す）
- `store` … 新しい事実 → 新規ファイル

書かないもの: コードやgit履歴から分かること、この会話でしか意味がないこと、秘密情報。

## 3. 書式（1ファイル1事実）

```yaml
---
name: <ファイル名と同じ kebab-case>
description: <1行。次回の判断がどう変わるか。検索で当たる語を入れる>
metadata:
  type: user | feedback | project | reference
  created: <YYYY-MM-DD>
---
<事実。feedback/project は **Why:** と **How to apply:** の行を続ける。関連は [[他の記憶のname]]>
```

- `---` は**必ず1行目**（前に空行やBOMがあると検索から永久に漏れる）。
- 役割（agent層）の記憶は `agents/<役割名>/` に置き、`tier: agent` と `agent: <役割名>` を必須とする。
- 雛形は `python bin/memory.py add <name> --type <種別> --description "..." [--global] [--agent <役割名>]` で作る。書いたら `python bin/memory.py lint`。
- 相対日付（「来週」）は絶対日付に直す。global に書いたら `MEMORY.md` に `- [題](file.md) — 一言` を1行足す。

## 4. 取り出し方

```
python bin/memory.py search "<語>" --type feedback      # 記憶の種別で絞ると精度が上がる
python bin/memory.py search "<語>" --agent <役割名>     # 特定の役割の記憶だけ
```

- **着手前に1回引く**（同じ失敗の再発を防ぐ最安の手）。
- 検索は1つの問いにつき**合計3回まで**。出なければ結論は「今回の条件では未発見」（「無い」とは書かない）。
- 索引は search 時に自動で作り直される（記憶の更新が索引より新しければ再構築）。
- 要約を書くときは原文への参照（パス）を残す（上位=構造・下位=証拠。戻れない要約を作らない）。

## 5. やらないこと

- 記憶フォルダの全文読み（棚卸しは frontmatter だけ読めば足りる。全文の約1/6の量）。
- 自分の記憶を自分で global へ昇格させること（昇格は別の役割か週次レビューが判定する）。
- 自動削除（書くなら cutoff検査・削除割合の上限・最小保持数・監査ログの4点が必須。）。
